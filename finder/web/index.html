Storefront requests/sec, direct connection. 5 is the measured ceiling — at 10 the edge bot-challenges ~97% of requests within about twenty seconds and the scan produces nothing for the rest of the run. Backing off afterwards does not clear it. With proxies configured this is raised automatically to rotation size x per-proxy rate.
It is a lever when hosts are slow: a host that fails HTTPS then retries HTTP holds a worker ~16s, so 300 workers ≈ 19/s ceiling. Too few and HTTP starves; too many and the DNS stage steals the event loop.
This one is a throughput lever — DNS is ~170 lookups per domain found. Measured on real domains: 400→691/s, 800→1078/s, 1600→1370/s. Higher wins until resolvers time out. Watch dns / sec above.
Per-resolver pacing. 0 = off, which is the setting your fastest runs used. Pacing fixed a measured cliff in isolation but did not reproduce end to end — kept as a dial rather than a default.
Leave blank to use the 9 public resolvers. Enter 127.0.0.1 if you are running a local resolver (unbound) — no per-client throttle, which is what caps the public pool under load. Space or comma separated for several.
Previously-failed hosts retried before any fresh candidate is checked. 0 is the right answer while the backlog is large. With 697,000 dead hosts queued, re-feeding even 500 of them front-loads roughly the first 40 seconds of a run with hosts already known to fail — a short scan then finds nothing at all. Measured: 0 found with 500 re-fed, 27 found in the same 20 seconds with 0. Purge the backlog rather than draining it this way.
